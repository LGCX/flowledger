## Contract parity (P01-GATE parity test)

- `DomainErrorCode ⊆ ProblemCode` (proper subset, asserted as such).
- Set equality for: `PaymentOperation.type`, `PaymentOperation.status`, `Payment.authorizationOutcome`,
  `Payment.summaryStatus`, `normalizedError.category`, `normalizedError.retryDirective`,
  `noEffectProof` kinds, `providerEvidence.source`, reconciliation `reason`, ledger `operationType`.
- `ID_PREFIXES` equals every `^<prefix>_` pattern in `entity-ids.v1.schema.json`.
- `MAX_AMOUNT_MINOR` equals the money-schema bound (`1000000000000`).
- All five golden files parse and meet their row counts (14/10/8/7/6).

**Break-and-restore for the parity test** (each observed failing, then restored):

| Break                                                                           | Result                          |
| ------------------------------------------------------------------------------- | ------------------------------- |
| domain adds `PLANNED` to `SUMMARY_STATUSES`                                     | `Payment.summaryStatus` fails   |

| domain adds a `zz` id prefix                                                    | the prefix check fails          |

The second break initially "passed" because the test reads _generated_ output: editing the contract
without regenerating is invisible. Regenerating is part of the break, and that is the honest form of it.

## Defect found by this gate

`FC_NUM_RUNS=1000` failed two P01-T03 properties with `INTERNAL_ERROR/VALUE_MALFORMED`. `fc.date`
emits `Invalid Date` unless `noInvalidDate` is set. The implementation was correct — `toTimestamp`
throws on an Invalid Date, since it is a programmer error rather than client input — and the generator
was wrong. Fixed test-only in `a456324 fix(domain): stop the timestamp properties generating Invalid
Date`, which reopens P01-T03 and is merged before this gate. Default run counts (200) never reached it.

## Deliberately not asserted here

- Ordered enum comparison. Order carries no meaning for a closed vocabulary and would fail on harmless
  reordering while still missing a real divergence; the parity test compares sets and reports which
  value moved.
- Database-level halves of the refund race, capture-below-minimum, and reservation properties. Those
  need real PostgreSQL and belong to P05, as the plan states in the traceability table.
