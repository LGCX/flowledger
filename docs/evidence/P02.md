## The committed fixture

`test/fixtures/db/P02.sql` is the populated M2 database P03+ migrate forward from. `test/integration/db/migrate-forward.test.ts` restores it into an empty database and asserts:

- `migrate()` applies **zero** files — the dump already carries every M2 migration;
- every payment satisfies the aggregate rules when the deferred constraints are set immediate;
- every outbox row still carries its hot envelope, so nothing was lost in the round trip.

It contains **no terminal operations** (risk R8): P06 adds an evidence foreign key to operations, and a
terminal operation would need evidence rows this fixture cannot invent before P06 exists.

## Docker Compose walkthrough (resolved)

`pnpm db:up` → `db:migrate --bootstrap` → `db:migrate` → `db:seed` → `db:migrate` now runs end to end on a
clean volume: **10 applied**, then **0 applied / 10 skipped**, then three credential lines from the seed,
then **0 applied / 10 skipped** again.

It took two fixes, both found only by running it:

1. **Port shadowing.** A local Homebrew PostgreSQL 14.18 owned `127.0.0.1:5432`, and Docker published the
   same address, so the CLI reached the _local_ server. The symptom was a syntax error at `INHERIT` in
   `0200_foundation.sql` — valid PG16+ syntax rejected by a PG14 server. `POSTGRES_HOST_PORT` now makes
   the mapping configurable, and `pnpm db:up` compares the `version()` seen through the published port
   with the container's own and refuses to continue when they differ.
2. **Database ownership.** The PostgreSQL image creates `POSTGRES_DB` owned by the superuser, so the
   migration owner could not create in `public` (`permission denied for schema public`).
   `bootstrapDatabase` now takes ownership of an existing database, which is what its contract already
   claimed.

Also added: `db:migrate` and `db:seed` scripts, which the plan assumed but `package.json` did not have.
